## 2026-08-24

The whole v1, planned and built in one session, three days before real data arrives. Every design decision below was Shivam's; Claude surfaced options with one recommendation and a tradeoff each.

- **Form audit first.** The new Fall availability form was checked page by page against the grid before anything was built. One data-corrupting defect found: the weekday ranking shows five rows (Mon-Fri) but ranks 1-4, while its own text says Mon-Thu and the weekend section calls Friday a weekend. The grid settles it: every Friday is a weekday evening shift. Fix list relayed to the duty leads against the 08/28 deadline; also flagged that the weekend checkbox conflates day and time preferences.
- **The two external inputs the spec was blocked on both landed.** Pairing period: Sept 8-13 returners only, Sept 14-Oct 18 experienced+new (exactly 4 duty weeks around the Sept 21-27 gap). Duty calendar: the grid xlsx, full quarter Sept 8 to Dec 13, holidays written as "Holiday" across the slot cells.
- **Grid measured: 138 shifts, 448 seats, three rule blocks** (32 returners-only, 144 pairing, 272 normal). This is what made D1 obvious: pairing front-loads the 17 experienced RAs, and only balancing the whole quarter at once nets everyone out to fair totals.
- **Feasibility model built and proven before fairness existed.** Hard rules only: availability, exact fill, no same-day back-to-back weekend shifts, returners-only, pairing composition. OPTIMAL, 448/448 seats, 0 violations from a validator that shares no code with the solver.
- **The unfair-but-legal schedule made the case for fairness better than argument.** Without an objective, the 3 LRAs soaked up 47-53 shifts each while some new RAs got 0. Nothing broke; nobody would accept it.
- **Fairness shipped: minimax over derived targets.** Targets 11 / 10 / 5 come from `compute_targets()` (new = baseline, returner = one less, LRA = half), never hardcoded. Soft goals only (F1), protect the worst-off person (F2), LRAs pulled to 5 with a heavier weight (F3). Result: max deviation 1, LRAs all exactly 5.
- **A diagnostic caught what the averages hid: 3 new RAs had zero pairing-period shifts.** Perfect quarter counts, no training. Shivam confirmed the pairing period exists to train new RAs, so a soft floor shipped: every new RA gets at least 2 pairing shifts, weighted above the fairness terms, flagging anyone it cannot seat. After: 0 below floor, max deviation still 1.
- **Flat scripts restructured into a package** (`models` / `grid` / `synthetic` / `solver` / `roles` / `validate` / `export` + CLI + 6 unit tests). Every rule constant lives once, in `models.py`. Role slotting is seeded, so identical inputs give identical schedules.
- **Formatter shipped: the filled xlsx matches the leads' sheet exactly.** Same headers, week label once per week, holiday rows preserved and shaded, Exceptions listing blackout RAs once per date, Arial throughout. Spot-checked by reading rows back out of the file, not by trusting the writer.
- **A wrong judgment call, caught the same hour it was flagged.** Claude read Primary as a leadership role and made the experienced RA always Primary on 2-person pairing shifts. Shivam corrected it: Primary/Secondary are the first (7:30) and second (9:30) walks, done by the pair together; during the pairing period every walk pair is 1 experienced + 1 new, and on 2-person shifts the label order means nothing and is now randomized. The wrong reading is scrubbed from code, docstrings, and the test suite, and the corrected semantics are verified in the output: all 28 pairing-period evening shifts carry mixed Primary and Secondary pairs.
- **Committed to AICC** at `technical-projects/ra-scheduler/code/`, commit `6f792fc`, package + tests + README only, no generated artifacts. A dedicated repo is planned; Shivam creates it, and the public/private call carries the data rule: code can go public, real names never.
- **Dedicated repo live: `ssinghal732/ra-scheduler`, private, commit `28959ca`.** Operator docs are held out through `.git/info/exclude`, which is local, so even their filenames never reach GitHub. `.gitignore` blocks `*.xlsx`, `*.csv`, and `*.json`, so a real grid or a filled schedule can't be committed by accident.
- **Pre-solve check shipped (`preflight.py`, 11 tests).** CP-SAT reports infeasibility as one word. This counts the arithmetic first and names the date attached to each problem: seats against eligible people free per shift, demand split by tier per block, and the data faults that masquerade as scheduling conflicts (an RA available for nothing, availability keys matching no shift in the grid). It never blocks the run, and if the solve fails anyway the pipeline reprints what preflight already flagged.
- **Pipeline verified on the laptop, not just in the sandbox.** `ortools` and `openpyxl` installed into `(base)`, then a full run against a stand-in grid generated to the documented shape: 138 shifts, 448 seats, 4 holiday rows, OPTIMAL in 27s, 0 violations, max deviation 1. Proven by reading rows back out of the output file: no new RA seated in the returners-only week, 28 of 28 pairing-period evening shifts with both walk pairs mixed, holiday rows intact. What this does not cover is `grid.py` against the leads' actual workbook, which is still the first thing to try on 08-27.
- **`grid.py` confirmed against the real workbook.** Reads `26-27 RA Duty Schedule.xlsx` with no errors, and every number matches what was measured by hand in July: 138 shifts, 448 seats, 86 duty dates, 4 holiday rows, blocks at 6/32, 28/144, 52/272. Full pipeline run on the real grid: OPTIMAL, 0 violations, max deviation 1. The stand-in grid was only needed until the real file was located; every module is now exercised against real input except availability, which is still the one open piece.
- **The check got rewritten twice for claiming more than it caught.** The first block-level version summed available slots against seats, which can only fall short when some shift is already short, so it was redundant. Splitting demand by tier fixed that: the pairing block needs 72 experienced seat-fills specifically, and 17 experienced RAs can miss that while every shift still shows enough people. Then the test written to prove it fires kept failing, which showed the blocking arm only triggers when a date pairs Afternoon with Evening, the one combination H3 forbids. Kept as a narrow backstop, labeled as one. The check likely to earn its keep on 08-27 is the stray-key one: the likeliest cause of a failed solve is a parser emitting keys the grid doesn't know, not anyone's calendar.

- **Last year's schedule replayed, and it moved a decision.** Ran the 25-26 Fall sheet (148 shifts, 480 seats, 45 names) through `validate.py`: every shift carried the right headcount, and 6 findings came back. Five trace to one date where a single name fills all 8 slots; the sixth is a genuine Morning-to-Afternoon back-to-back. Then parsed last year's real form responses (42 of them) and checked the schedule against what people declared.
- **The replay found its own limit.** That workbook holds an `RA Duty Swaps` sheet with 355 records, so the schedule sheet is the plan and not the record. The back-to-back date alone saw 7 swaps. "Replay last year," which the v1 spec listed as a validation step, is therefore weak evidence: it validates a plan that was amended 355 times. Kept as a parser shakedown, dropped as proof.
- **Four parser decisions locked.** Key on ucsd email, never names (only 4 of 45 names matched exactly last year). Blackout dates MM/DD only, chopped at position 5, since the new form specifies the shape and Shivam hand-checks before the parser runs. Non-submitters stop the run and get listed rather than defaulting to available or unavailable, because both defaults produce a plausible schedule built on someone the tool knows nothing about. No NLP: 43 hand-checked rows a quarter don't need it, and a regex that fails says so while a model guesses confidently.
- **Documents folder added** (`94e8fd6`): a plain-language walkthrough of every module, also published as a shareable page.

## 2026-08-26

- **Availability tab added to the exported workbook.** One row per RA in the shape the form collects: tier, the five weekday cells, dates they cannot work, shifts they could have worked, shifts they got. The weekday cells are derived from the availability set rather than stored, so the sheet cannot drift from what the solver actually saw. Written on every run, not just synthetic ones, so anyone reading a schedule can check an assignment against the availability behind it.
- **Output filename now forced to carry SYNTHETIC** when availability is invented. Asking for `fall_2026_final.xlsx` produces `fall_2026_final_SYNTHETIC.xlsx` and nothing else; the caller does not get to choose. Idempotent, and flips to real behaviour with one line when `--availability` lands.
- **A gap found by asking the right question.** Shivam noticed the Availability tab showed no preference data and asked whether preferences were in the solver. They are not, which was known and parked. What was not known: the 08-24 checkpoint recorded "each RA is assigned ONE recurring weekday" as a confirmed model, and the solver never implemented it. Measured against last year's real schedule to settle the shape: only 5 of 44 RAs had a single weekday, and the median RA did 62% of their weekday evenings on their most-used day against our 50%. So the leads pull toward a day rather than fixing one. Decision: build the soft pull, not the hard assignment. Tracked as AiCC task #4, blocked on the parser.
